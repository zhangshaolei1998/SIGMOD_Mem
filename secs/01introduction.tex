LLM agents increasingly interact with users across multiple sessions, relying on past preferences and experiences to provide context-aware responses~\cite{memgpt,locomo,longmemeval}.
\emph{Memory} is the persistent data underlying these interactions, which retains information from past interactions and serves queries issued by the agent.
As interaction histories grow, effective memory management requires organizing and maintaining stored information while efficiently processing memory queries from the agent.

Both the AI and database communities have made progress in \emph{memory organization} and \emph{query processing} for LLM agents.
In the AI community, MemGPT manages context hierarchies~\cite{memgpt}, Mem0 extracts and updates facts~\cite{mem0}, and Zep and A-MEM organize temporal relationships and linked notes~\cite{zep,agenticmem}. RMM, MemRL, and Live-Evo learn retrieval priorities or experience utilities from feedback~\cite{rmm,memrl,liveevo}, while MemR$^3$ adapts retrieval through reflective control~\cite{memr3}.
In the database community, VikingMem manages events and entities through selective extraction, state updates, and temporal consolidation~\cite{vikingmem}. MemLens estimates the marginal contribution of memory units to response quality and uses these estimates for retention and retrieval~\cite{memlens}.

\runin{Limitations}
Despite these advances, existing memory systems provide \emph{limited support for continually improving memory management based on previous query executions}.
As summarized in Table~\ref{tbl:positioning}, this limitation manifests in two aspects.

First, \emph{memory organization} primarily focuses on user knowledge without systematically retaining memory-use experience.
Consider Alice's March activities in Figure~\ref{fig:motivating}: a hike organized by Ava, a pottery class organized by Ben, and a ride organized by Cara.
For \emph{Whom should I contact to repeat my March outdoor activities?}, memory retrieves whether each activity was indoor or outdoor,
along with its organizer. The agent identifies the hike and ride as outdoor activities and returns Ava and Cara, excluding the indoor pottery class. However, storing these facts alone does not capture which information contributed to the answer or the cost of retrieving it.
Consequently, subsequent queries cannot reuse this experience to prioritize useful evidence or avoid unnecessary retrieval.

Second, \emph{query processing} primarily focuses on retrieving relevant facts without explicitly handling query-specific computations. For example, finding an activity organizer requires a single fact, counting outdoor activities requires examining all activities, and finding the organizer of the longest outdoor activity requires comparing durations before identifying the organizer. A generic retrieval workflow may return relevant facts without completing these computations. Moreover, without considering previous execution experience, the system may repeat completed work or waste computation on already verified facts.

\runin{Our Proposal}
We propose \sys{}, a \emph{self-evolving memory management system} for LLM agents. The key idea is to jointly manage conversation history and memory query history, using execution feedback from past queries to improve subsequent query processing.
Realizing this design raises two technical challenges.

\stitle{Challenge C1: Accurate Memory-Use Attribution.}
The first challenge is to maintain query execution history by accurately attributing query results to their supporting facts.
For example, Alice's contact query returns Ava and Cara, but the indoor pottery class is also needed to exclude Ben.
Recording all retrieved facts includes irrelevant evidence, while tracking only facts mentioned in the answer misses evidence used for exclusion.

To address this challenge, \sys introduces a \emph{three-level memory architecture} (Section~\ref{sec:overview}).
Raw memory retains conversation history, first-order memory stores facts extracted from conversations, and second-order memory maintains memory query history.
\sys tracks the sources and versions of retrieved facts, together with their reported use, execution outcomes, and costs. For derived results, derivation links identify supporting facts and propagate usage attribution to these facts. The resulting query execution history provides reusable feedback for subsequent query processing.

\stitle{Challenge C2: Adaptive Memory Query Processing.}
The second challenge is to construct and execute query plans that accommodate different evidence requirements while exploiting historical execution feedback.
For example, Alice's longest-activity query requires comparing activity durations before retrieving the corresponding organizer.
Previously verified facts can be reused, while missing information requires additional retrieval.

To address this challenge, \sys combines \emph{query planning}
(Section~\ref{sec:framework}) with \emph{cost-aware execution}
(Section~\ref{sec:executor}).
\sys constructs query plans for single-fact retrieval, independent composition, and dependent composition, explicitly representing their evidence requirements.
Using the current evidence state and historical execution feedback, \sys reuses verified facts, allocates query-specific execution budgets, and adaptively selects further retrieval
operations. Execution outcomes and costs are recorded in second-order memory, enabling subsequent queries to benefit from accumulated experience.

\runin{Contributions}
Our contributions are summarized as follows.
\begin{itemize}[leftmargin=*,nosep]
\item \textbf{Self-evolving memory management.}
We introduce \sys{}, a memory management system that continually evolves both stored information and query processing by retaining conversation history and memory query history, and using historical execution feedback to improve subsequent queries.

\item \textbf{Memory organization and query processing.}
We develop a three-level memory architecture that maintains conversation history, extracted facts, and memory query history with source and version tracking.
We further propose query planning and cost-aware execution that handle different evidence requirements, reuse verified facts, and adapt execution effort based on historical feedback.

\item \textbf{Experimental evaluation.}
Across eight long-term memory benchmarks, \sys{} matches or outperforms the strongest evaluated prior system on every benchmark, as shown in Figure~\ref{fig:scoreboard}, with an average improvement of 2.6 points.
On \membench{}, it achieves higher accuracy with 50.7\% fewer memory-side LLM calls than a fixed three-call budget. Experiments with eight LLM backbones further evaluate its generality.
\end{itemize}
