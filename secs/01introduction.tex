\section{Introduction}
\label{sec:intro}

\input{figures/tex/introduction_example}

Memory is the foundation of a personal Large Language Model (LLM) agent. It allows the agent to remember a user's preferences, track promises and plans across conversations, and answer questions about the past. As agents are deployed in more settings, from personal assistants to customer service bots, the interaction history they accumulate grows rapidly, reaching hundreds of thousands of tokens per user, and in some deployments exceeding a million~\cite{mem0,memgpt,zep}. This growing volume makes it increasingly difficult to find the right information at the right time, and requires a systematic way to \emph{manage} agent memory.

Yet today's memory systems store this data but do not manage it. Systems differ in what they store --- raw transcripts~\cite{longcontext}, embedded chunks via Retrieval-Augmented Generation (RAG)~\cite{rag}, extracted facts~\cite{mem0}, paged tiers~\cite{memgpt}, or graph edges~\cite{zep} --- but at query time every one follows the same pipeline: retrieve relevant passages, then generate an answer, regardless of what the query asks. No system distinguishes whether a query needs a simple fact lookup, an enumeration of multiple records, or a comparison across entries, and no system learns which stored memories are more useful than others. As Figure~\ref{fig:motivating} illustrates, this leads to two limitations.

\stitle{Two Limitations of Current Systems.}
%
\begin{itemize}[leftmargin=*]
\item \textbf{Static memory operations.}
Every query goes through the same retrieval pipeline, and no system records which memories contributed to correct answers. As a result, systems fail on queries that a single retrieval pass cannot serve, such as counting candidates across sessions or comparing values from distant passages~\cite{ruler}, and every query starts from scratch as if the user had never asked anything before.

\item \textbf{High cost of memory access.}
No system differentiates queries by difficulty. A simple fact lookup that could be answered in one LLM call receives the same computational budget as a complex aggregation that benefits from multiple samples, wasting calls on easy queries while hard queries receive no extra allocation.
\end{itemize}

Both limitations stem from the same root cause: agent memory is treated as a flat store with no management layer. Database management systems solved the analogous problem for structured data decades ago: schemas organize what is stored, query planners choose how to answer each query, and cost models control how much computation each answer spends~\cite{selinger1979,graefe1993}. Agent memory calls for the same separation of concerns, yet no existing system provides it. Building such a system raises three challenges.

\stitle{Three Challenges for Memory Management.}
%
\begin{itemize}[leftmargin=*]
\item \textbf{Architecture: what to store and how to answer.}
Agent memory is unstructured natural language. To manage it, the system needs to impose structure on the stored data, recognize different types of queries, and route each to specialized logic, ideally without spending an extra LLM call.

\item \textbf{Performance: how memory retrieval improves over time.}
A good memory system should get better as it serves more queries for the same user, just as a database improves its indexes as it collects workload statistics. This requires a feedback loop that records which stored entries helped answer past queries and uses this signal to reorganize the memory for subsequent queries, a mechanism that no existing agent memory system implements. The difficulty is that no ground-truth answers are available at deployment time, so the system must define ``useful'' without external supervision.

\item \textbf{Efficiency: how to control the cost of memory access.}
An LLM call is the dominant cost unit, and drawing multiple independent answers to the same query (Self-Consistency~\cite{sc}) multiplies it. A system that spends the same budget on every query wastes calls on easy queries that do not need them, and cannot reallocate to hard queries that do. The system needs a cost model that assigns different budgets to different query types and stops spending when additional calls cannot change the outcome.
\end{itemize}

\stitle{Our Proposal.}
To address these challenges, we propose \sys{}, a memory management system for LLM agents that treats agent memory as managed data. As shown in Figure~\ref{fig:framework_overview}, \sys{} consists of a framework and two optimization layers.

\begin{itemize}[leftmargin=*]
\item \textbf{Framework: Typed Catalog, Query Planning, and Operators} (Section~\ref{sec:framework}). To address the architecture challenge, \sys{} organizes raw sessions into a typed catalog of entities, events, relations, and attributes. A lightweight planner recognizes three query patterns, \point{} (fact lookup), \agg{} (aggregation), and \cmp{} (comparison), by matching keywords in the query, with no LLM call. Each pattern is handled by a specialized operator that defines a fixed sequence of steps for answering the query.

\item \textbf{Second-Order Memory} (Section~\ref{sec:secondorder}). To address the performance challenge, \sys{} logs which catalog entries appeared in answers that two independent samples agreed on, and ranks those entries higher for subsequent queries. This is a workload feedback loop, analogous to self-tuning indexes in classical databases~\cite{chaudhuri1997autotuning}, applied to agent memory for the first time.

\item \textbf{Cost-Aware Executor} (Section~\ref{sec:executor}). To address the efficiency challenge, \sys{} assigns different LLM call budgets to different query patterns: one call for simple lookups, up to three for hard aggregation or comparison queries. It further stops early when two samples already agree, using agreement as a signal that additional calls are unnecessary.
\end{itemize}

\begin{example}
\label{exam:intro}
Alice asks her agent \emph{``How many of my events involve outdoor activity?''} after six earlier questions. A full-context baseline scans the whole history and answers 5, miscounting evidence scattered across sessions, while the correct answer is 3. A graph memory retrieves six related nodes but never evaluates the condition for each event, and the model guesses 4. \sys{} routes the query to \agg{} (aggregation). The second-order memory promotes event entities that appeared in answers to earlier questions, so the operator reads the relevant events first. It evaluates each candidate with an explicit yes/no judgment and answers 3. The cost-aware executor draws two independent samples; both return 3, so it skips the third sample and commits after two LLM calls. Table~\ref{tbl:casestudy} gives the full trace.
\end{example}

\stitle{Contributions.}
We summarize our contributions as follows.

\noindent
(1) We formulate agent memory as a data management problem and build \sys{}, the first memory system that provides a typed catalog, a query planner, and specialized operators for LLM agent memory (Sections~\ref{sec:overview} and~\ref{sec:framework}).

\noindent
(2) We introduce \emph{Second-Order Memory}, a workload feedback loop that improves memory quality over time for each user without supervision (Section~\ref{sec:secondorder}), and a \emph{Cost-Aware Executor} that reduces LLM calls by half while maintaining accuracy (Section~\ref{sec:executor}).

\noindent
(3) We evaluate \sys{} on eight long-term memory benchmarks and eight LLM backbones. \sys{} matches or improves the strongest prior system on every benchmark, by an average of $2.6$ points and up to $5.6$ points on \lmes{}, while reducing LLM calls by $50.7\%$ relative to a Uniform-$K{=}3$ reference (Section~\ref{sec:experiments}).
